# Sandbox developer experience: running findings

Everything we hit against the Whop sandbox on 2026-09-08 while building Ledgerly, with the evidence path. This is the source list for the assessment's "three things you would change first." Keep adding; prune at the end. Verified means we reproduced it against `sandbox-api.whop.com` or `sandbox.whop.com` today.

## Money and verification

1. **Sandbox payouts do not exist, and the docs say so only in a footnote.** `docs.whop.com/developer/guides/sandbox` lists "Payouts: payout functionality isn't available yet" under Known limitations. The assessment's Part 1 step 4 asks for embedded payouts, a fee markup and a payouts portal. Lists return empty, `POST /payouts` needs a `payout_method_id` no sandbox seller can obtain. Evidence: `packages/whop/fixtures/run-2026-09-08d/list-payout-methods-us.json`, `create-payout-us.json`; readback `run-2026-09-08e-BUILD-15.json`.
2. **Connected-account onboarding hands off to Sumsub with no test path.** The `account_onboarding` link collects personal details, then requires an identity document and a webcam liveness check. The Verifications API offers hosted, document upload, or a share token from a prior real verification. No test applicant, no auto-approve, no magic values. Evidence: `run-2026-09-08d/verification-*.json`, agent report; Sumsub screen reached at `sandbox.whop.com/verify-identity/biz_m3qw7Bln9ZxZqN`.
3. **The platform KYC opened a second, undocumented gate.** After identity approval flipped `transfer` and `standard_payout` to active, a new required action `submit_information_request` appeared with `blocked_capabilities` covering every payout and transfer capability, "typically less than 24 hours" to review. Nothing in the docs prepares a developer for verification being a two-step process. Evidence: `GET /accounts/biz_RlL9WP9TIBVXmr` at 22:05Z and 22:07Z.
4. **Application fees settle on a two-day clock even in sandbox.** Four $2.00 fees post as `pending` with `available_at` two days out. `POST /transfers` answers "You cannot transfer funds out of your pending balance", `POST /payments/{id}/refund` answers `not_enough_balance`. A sandbox should let you settle instantly or document the delay. Evidence: `GET /financial-activity?account_id=biz_RlL9WP9TIBVXmr`; readbacks `run-2026-09-08e-BUILD-11.json`, `-BUILD-12.json`.
5. **The sandbox dashboard cannot store a card.** Deposit on the balance page shows "Unable to load deposit details. Please try again." on every try, so there is no `pmt_` id for `POST /topups`, and `POST /setup_intents` needs a confirmation token from a frontend element. The topup step in the assessment cannot be done from the sandbox as shipped. Evidence: ego-browser session, 22:20Z; `GET /payment_methods?account_id=` empty.

## Keys and permissions

6. **API keys cannot be managed by API.** `POST /api_keys` and `GET /api_keys` return "This resource type is not currently supported" for a bare body, and a 403 "Company API key is not authorized for the developer:manage_api_key scope" for the documented body; the permissions catalog marks that scope as not grantable to any key type. The docs publish full request and response schemas for both. Evidence: `run-2026-09-08d/create-api-key-*.json`, `list-api-key-permissions.json`; readback `run-2026-09-08e-BUILD-21.json`.
7. **A platform owner cannot mint a key for a connected account in the dashboard either.** Viewing the connected account's Developer page as the platform owner, Create fails with "You don't have permission to manage who can access this company. Ask a company owner to make this change." Signing in as the seller's own user works, but that user still sees the "viewing a connected account of ledgerly" banner, so the ownership model is unclear on screen. Evidence: `run-2026-09-08d/seller-key-dashboard-permission-error.json`, `seller-key-created.png` (private capture, kept outside git under the endpoint-audit run directory).
8. **`GET /accounts/{id}` is gated on `company:balance:read`, not on a read scope.** A key with `company:basic:read` and `payment:basic:read` cannot read its own company record. The 403 names the missing scope, which is good, but the mapping from endpoint to required scope is not in the reference. Evidence: `run-2026-09-08d/seller-key-accounts-de.json`.
9. **"Minimum scopes" is not discoverable up front.** The permissions catalog has 258 actions; there is no per-endpoint "requires" line in most references except topups. The assessment asks for a minimum-scope key on step 1; the only way to find the minimum is trial and 403.

## API shape and docs

10. **Retracted: `country` is honored.** Run a's DE and BR sellers read back as `us` because our adapter at the time omitted `country` from the body (run-a readback limitation), not because the API ignored it. Accounts created today with `country: CA`, `KR`, `PT` read back `ca`, `kr`, `pt`. Evidence: `run-2026-09-08e/store-wiring-create-account-*.json`. Kept here so nobody re-reports it.
11. **`parent_company_id` in the assessment and older examples is not a request field.** Parent is derived from the key. Documented in `docs/answers/improvements.md` item 2.
12. **The beta checkout configuration schema has no `application_fee_amount`.** Only the legacy endpoint carries it, and the create response never echoes the fee, so the platform has to persist it locally. Documented in `improvements.md` item 1; evidence `run-2026-09-08e-BUILD-09.json`.
13. **Ledger paths in the docs snapshot do not match the API.** `/ledgers`, `/ledger_accounts`, `/ledgers/activity` are 404; the working path is `/financial-activity`. Evidence: `run-2026-09-08d` ledger-recon probe, `run-2026-09-08c-BUILD-10.json` limitation.
14. **Two names for the same withdrawal event.** `withdrawal.updated` and `payout.updated` both fire (assessment Part 3), and the payout webhook payload has `company_id` but no `account_id`. Documented in `docs/answers/debug.md`.
15. **Sandbox responses link to production.** `required_actions[].cta` and error messages point at `https://whop.com/...`, not `sandbox.whop.com`; a developer who clicks lands on the wrong account. Evidence: `GET /accounts/biz_RlL9WP9TIBVXmr` `required_actions`.
16. **Webhook test fire reports the receiver's status, not its body, and did not record a delivery until the secret was live.** Run c saw a 500 with no delivery row and nothing to replay; run e saw a delivery and a working replay. The docs do not say a failed test is not persisted. Evidence: `run-2026-09-08c-BUILD-19.json` vs `run-2026-09-08e-BUILD-19.json`.
17. **`child_resource_events` wording is ambiguous, and the answer is "both".** The docs say the flag "sends events only from its connected accounts". Tonight the one platform webhook delivered `payment.succeeded` for connected-account payments (biz_pt7b2NAryKwRGh, biz_RduxG8ScXWC4nB, biz_uOEIplOLcdfJUi) and for the platform account's own payments (biz_RlL9WP9TIBVXmr, platform-charge orders). A consumer that maps events to sellers by `account_id` alone quarantines the platform-charge payments; ours did until it learned to resolve by `checkout_configuration_id`. Evidence: production `webhook_inbox` rows 23:29 to 23:40 UTC; `run-2026-09-08e-BUILD-19.json`.
18. **No unsuspend.** `POST /accounts/{id}/suspend` is one-way; `/unsuspend`, `/reactivate` are 404 and `status` is read-only on PATCH. A platform that suspends by mistake, as our run c did to the demo US seller, has no recovery path. Evidence: `run-2026-09-08d/unsuspend-attempt-01.json` and siblings.
19. **Idempotency keys are body-strict with a generic error.** Reusing a key with a changed body returns "This Idempotency-Key was already used with a different request" without saying which field differed. Evidence: `run-2026-09-08e/create-account-throwaway.json` first attempt.
20. **Fake email domains are rejected on account create.** `@example.com` fails with "The email you provided does not accept incoming mail", so sandbox fixtures need real inboxes. Evidence: same file.

21. **Every API-key action in the dashboard re-prompts an emailed identity code.** Creating a key, revealing it, and opening it to edit each sent a fresh six-digit code to the seller's inbox within twelve minutes, on top of the sign-in code. Reasonable for production; in a sandbox it turns a two-minute task into an inbox relay. Evidence: codes at 22:33, 22:36, 22:44, 22:48 UTC to the DE seller alias.

22. **A per-seller key works only from the seller's own session, and scope hides rather than denies.** Signed in as the DE seller's user, the dashboard minted a Company API key. With `company:balance:read` it reads its own account (200) and gets 404 "Account not found" for the BR seller and for the platform, not 403. Nested create with that key returns 400 "A connected account cannot create its own connected accounts", which is the business rule the assessment asks you to observe and which the platform key never reaches (it silently ignores `parent_company_id` and creates a sibling). Evidence: `run-2026-09-08d/seller-key-scoped-accounts-{de,br,platform,nested-post}.json`, `seller-key-created.png` (private capture, kept outside git under the endpoint-audit run directory).

23. **The hosted checkout rejects `.test` emails and shares one session per browser.** `buyer@ledgerly.test` fails Whop's live validator ("Please enter a valid email address"), so test fixtures need a routable domain. Two checkouts opened in one browser profile swap each other's order mid-form; opening each order's own `purchase_url` gives an isolated guest checkout. Evidence: purchase agent reports 23:2x to 23:4x UTC, `docs/lanes/architecture/store-purchases/`.

## Candidates for the final three

Strongest, because each blocked an assessment step outright and each has a one-line fix:

- Sandbox has no payout, no instant settlement, and no way to store a card (items 1, 4, 5): the whole "two money flows" step cannot complete in sandbox as shipped. Fix: a sandbox-only settle-now switch and a documented test payment method.
- Connected-account verification has no test path and the platform's own KYC is two gates deep (items 2, 3): onboarding cannot be completed as a seller. Fix: a Sumsub test applicant in sandbox and a doc section on the information-request step.
- API keys are documented but unusable by API, and the dashboard permission model for connected accounts is unclear (items 6, 7, 8, 9): per-seller keys cannot be automated. Fix: either ship `developer:manage_api_key` for Account API keys or mark the endpoints session-only and publish a per-endpoint required-scope line.

Items 10, 13, 15 are smaller but cheap, and worth a sentence each if space allows.
