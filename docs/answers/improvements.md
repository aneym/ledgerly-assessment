# Part 4: three improvements

Three proposals based on the September 8, 2026 documentation snapshots and saved sandbox observations. Doc paths point at local files in `docs/sources/whop/`; these are dated observations, not a fresh review of the live documentation.

## 1. Point the connected-account payments guide at an endpoint that still has application_fee_amount

What a developer experiences: the platforms guide for collecting payments on behalf of connected accounts shows Python and TypeScript examples that set `application_fee_amount` on a checkout configuration, and its "create a checkout configuration" link goes to the legacy endpoint, `api-reference/checkout-configurations/create-checkout-configuration`. That endpoint does have the field. But the beta version of the same operation, `api-reference/beta/checkout-configurations/create-a-checkout-configuration`, does not; its request schema lists `account_id`, `billing_period`, `currency`, `description`, `plan_type`, `product_id`, and more, with no fee field at all (`docs/sources/whop/CONTRACT-NOTES.md`). A developer who follows the beta migration path, or who lands on the beta reference page first while building the same feature the guide describes, has no documented way to charge an application fee. They either stay on the legacy endpoint indefinitely or guess that the fee has moved somewhere else in the beta shape.

Change requested: either add `application_fee_amount` to the beta checkout configuration schema, or add an explicit note on the beta reference page saying application fees are legacy-only for now and linking back to the guide's working example. Ledgerly's own sandbox adapter (`packages/whop/src/sandbox-adapter.ts`) builds its direct-charge checkout against the legacy endpoint for exactly this reason.

## 2. Reconcile parent_company_id in examples with parent_account in responses

What a developer experiences: assessment-era and some guide examples pass `parent_company_id` when creating a connected account, implying the parent relationship is set explicitly per request. The account creation reference for `POST /accounts`, `api-reference/beta/accounts/create-account`, lists no such field; its documented request body is `affiliate_code`, `blueprint_id`, `country`, `email`, `metadata`, `send_customer_emails`, `title`. The parent relationship instead comes back as a response-only field, `parent_account`, derived from the API key used to make the call; `parent_account_id` was replaced by `parent_account` on 2026-07-31 per the versioning changelog (`docs/sources/whop/CONTRACT-NOTES.md`). A developer copying the older example will send a field the API silently ignores, then be confused when the child account's parent is set by whichever key made the call instead of by anything they wrote in the body.

Change requested: remove `parent_company_id` from every example that still shows it, and add one sentence next to the account creation reference stating that parent is derived from the authenticating key, not from a request field. Ledgerly's sandbox adapter currently sends `parent_company_id` anyway, to record what the live API actually does with an unrecognized field, and that behavior is documented as a known gap in `docs/lanes/architecture/decision.md`.

## 3. Define what child_resource_events actually includes

What a developer experiences: the webhook creation reference describes `child_resource_events` twice, once in the request body and once in the resource schema, both times with the same sentence: "Whether to send events for child resources. For example, if the webhook is created for an account, enabling this sends events only from its connected accounts" (`api-reference/beta/webhooks/create-webhook`, quoted in `docs/sources/whop/CONTRACT-NOTES.md`). The word "only" reads two ways. It could mean the webhook receives child events instead of the parent's own events, or it could mean the webhook receives child events restricted to just the immediate children, as opposed to grandchildren too. For a platform account like Ledgerly's, which needs every seller's `payment.succeeded` and related events, this ambiguity decides whether the platform still needs a second subscription for its own account's events alongside the child one.

Change requested: rewrite the sentence to state plainly whether enabling this flag adds child events on top of the parent's own events, or replaces them, and confirm whether nested (grandchild) connected accounts are included. The later September 8 store purchase report records both connected-account and platform-account payments reaching the same webhook, followed by a routing fix for platform-account orders. That is observed behavior for this sandbox configuration, not a guarantee for every API version. The earlier open question in `docs/lanes/architecture/mock-strategy.md` predates that report. Update the documentation to state the contract explicitly, including whether nested connected accounts are supported. Source: `docs/lanes/architecture/store-purchases-2026-09-08.md`.
