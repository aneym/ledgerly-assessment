The integration code

Idempotent onboarding

Seller identity is mapped locally. Retries reuse the account relationship instead of creating a second seller.

Server-owned checkout

Amount, currency, seller, and the 8% application fee are computed and validated on the server.

Durable webhook processing

Signature validation precedes processing. The inbox deduplicates deliveries; financial-effect keys guard against duplicate ledger entries.

Reconciliation

The job compares provider payment and transfer records with the local ledger, and reports differences for investigation.

Part 3

Debugging the German withdrawal

The consumer mismatch

The missing account_id looks like a payload-contract mismatch: this event provides company_id, which we need to map to the seller. We'll validate against the schema for the supplied API version and handle unexpected payloads without crashing the consumer.

The duplicate posting

For the double-posting, I'll confirm how withdrawal.updated and payout.updated relate in your API version rather than assume they're interchangeable. Regardless, our ledger must ensure the same underlying money movement isn't posted twice. We'll deduplicate deliveries and enforce idempotency on the withdrawal and financial transition, not just the event name.

The pending withdrawal

I'll investigate the pending withdrawal before giving you a timeline. Two days alone doesn't establish a problem. I'll check its expected arrival, processing status, payout method, and any outstanding verification requirements.

My first reply

Thanks for flagging this. We'll investigate the consumer mismatch and duplicate postings separately from the pending withdrawal. Please send the withdrawal ID and both webhook event IDs so we can trace them. We'll check the seller's verification status and expected arrival before confirming a timeline. Please don't retry the withdrawal while we investigate.

Last thing

Three changes I'd make first

  1. Make the application-fee path clear

    The beta checkout schema omits application_fee_amount. Add the field or point developers to the supported legacy endpoint, so they can follow the connected-account guide without guessing.

  2. Explain how the parent account is chosen

    Align the examples with the account schema. State that the authenticating key determines the parent, and distinguish that from the response's parent_account field.

  3. Define child webhook coverage

    Say whether child_resource_events adds to or replaces parent events, and whether it includes nested accounts. A platform needs to know which subscriptions cover its ledger.

Who maintains what

Ledgerly owns its catalog, orders, seller mapping, fee rules, and local ledger. Whop provides connected accounts and payment and payout APIs. The integration maintainer owns the pinned contracts, webhook consumer, reconciliation, and regression tests. Operators investigate differences before authorizing a correction.
